# 开发日志：这个项目是怎么被一次次打脸的

> 这份文档记录开发过程中**真实发生的失败与修复**，不是功能清单。
> 所有数字来自运行输出，不是估算；每条都附了当时看到的现象和最后的改法。
>
> 写它的原因：Agent 系统里最容易骗过自己的是「它看起来能跑」。
> 下面这些坑，没有一个会在运行时报错——它们全都**静默地把结果变差**。

---

## 0. 一句话总结

**Agent 工程的难点不在单点，在组合。**
压缩、预算、工具报错、提示词、评测，每一块单独看都对，叠在一起就会互相抵消。
真正让我把项目从「能跑」推到「能测」的，不是新增功能，而是**给每个改动找一个能立刻报警的对照实验**。

---

## 1. 压缩把关键行丢了（最典型的一类）

### 现象

模型对一个 Jackson 反序列化异常给出：「`Caused by` 后无 detail message，当前证据不足」。

但原始日志里明明写着：

```
Caused by: com.fasterxml.jackson.databind.exc.InvalidFormatException:
Cannot deserialize value of type `java.util.ArrayList<java.lang.String>` from Object value (token `JsonToken.START_OBJECT`)
 at [Source: (String)"{"code":0,"data":{"price":null,"tags":{"a":1}}}"; line: 1, column: 62]
```

### 根因

压缩用正则白名单筛行。Java 堆栈的 `Caused by: com.xxx.InvalidFormatException:` 这行**末尾就是换行**，
真正有信息量的描述在**下一行**——而那一行不匹配任何正则，被当噪声丢了。

> **压缩机之把「看起来不像错误」的行当噪声，而真正定位到字段的 `line: 1, column: 62` 恰好长这样。**

### 改法

在「异常行」和「栈帧行」之间插入续行规则：

```python
continuation_left = 0          # 异常行之后允许跟随的描述行数
for ln in lines:
    if EXC_LINE.search(ln) and not FRAME_LINE.search(ln):
        keep.append(ln); continuation_left = 3
    elif continuation_left > 0 and ln.strip() and not FRAME_LINE.search(ln):
        keep.append(ln); continuation_left -= 1   # 续行：异常描述、at [Source:...] 定位
    elif has_stack and FRAME_LINE.search(ln) and frame_count < 20:
        keep.append(ln); frame_count += 1; continuation_left = 0
    else:
        continuation_left = 0
```

### 前后对比

| | 压缩后字数 | 压缩率 | 模型给出的定位精度 |
|---|---|---|---|
| 修复前 | 1635 | 94.7% | 「具体字段不明，证据不足」 |
| 修复后 | **1852** | **93.9%** | `data.tags` 是 JSON 对象，DTO 声明为 `List<String>`，`line 1, column 62` |

**多花了 217 字（+13%），换来了字段级定位。**

### 学到什么

> 压缩率和信息保真是同一件事的两面。你按「什么像错误」筛选，就会漏掉「长得不像错误但很关键」的行。
> 所以压缩之后**必须回原始日志抽样核对**，不能只看压缩率。
>
> 通用原则：**任何有损压缩都要能被反向验证。**

## 2. 连续三次「修 A 坏 B」

这一段是整个项目里最值得讲的部分：**我的每一次修复都引入了新的 bug**。

### 2.1 取回原文的工具，把原文又压回去了

`FetchToolResult` 的语义是「取回被压缩掉的原文」，但它返回的内容在进入上下文前，
**又走了一遍同样的压缩函数**——取回来和压缩前字数一模一样（都是 1852）。

改法：这类工具的结果跳过压缩，只做硬截断；同时给出提示：

```python
if tc.name == "FetchToolResult":
    if len(content) > config.TOOL_RESULT_MAX_CHARS:
        content = content[:TOOL_RESULT_MAX_CHARS] + "\n\n[超出 ... 已截断]"
```

### 2.2 修完 2.1，整套证据全丢了（最戏剧性）

**现象**：

```
[step 1] ↓ FetchErrorLog 压缩 30571→1852 字 (structure)
[step 2] ↓ FetchToolResult (0ms)          ← 修复生效，确实拿到了原文
...
当前证据不足，无法给出结论。
- 证据：两个工具的返回内容均已被移出上下文。
- 我还尝试用 FetchToolResult 取回，但句柄同样返回「已过期」。

步数=3  耗时=5191ms  tokens=4817+599  工具=4(失败1)
```

工具从 6 次降到 4 次，token 从 10451 降到 4817——**看起来是优化，实际是模型变瞎了**。

**根因：三个独立缺陷叠在一起**

1. **预算太小**：`BUDGET_TOOL_RESULTS = 6000` 字。日志压缩后 1852 字已占 31%，再塞 6000 字原文直接爆表。
2. **淘汰策略太笨**：`_enforce_budget()` 用 `tool_idx.pop(0)`——**永远从最早那条开始扔**。而排错场景里，**第 1 步的日志恰恰是所有后续推理的锚点**，扔了它后面全白做。
3. **占位符没有行动指令**：`[已过期] 该工具结果因上下文预算被移出`——模型看到后选择直接给结论，而不是重新取证。

**改法（四管齐下）**

① 淘汰按价值排序，不是按时间：

```python
def evict_order() -> list[int]:
    live = [i for i in idx_of() if not messages[i]["content"].startswith("[已过期]")]
    protect = live[-1]                      # 最新一条永不淘汰
    rest = [i for i in live if i != protect]
    rest.sort(key=lambda i: (
        0 if "FetchToolResult" in messages[i - 1].get("content", "") else 1,   # 补充材料先扔
        i,
    ))
    return rest
```

② 预算 6000 → 12000。

6000 当年是按「**单条**工具结果别太长」定的，但真正要管的是**累计量**——
日志 1852 + 取回窗口 2500 + 一条检索 2000 = 6350，第 3 步就破了。
12000 的算法：DeepSeek-chat 64K 上下文，中文保守按 1 字≈1 token，12000 字≈12K token≈**19%**，
其余 81% 要装 system prompt、每步 assistant 推理文本（8 步两三千字）、本次输出（两千字上下）和余量，合计不到 50%。
**它约等于当前最大单次场景的两倍，是「刚好让这起事故不再复现」的经验值，不是最优值**——往上加不触发淘汰、没有收益，往下减有两个已知坏点（6000 会破、3000 反复取证）。

③ `FetchToolResult` 改为返回「命中窗口」而非全文——以最新异常行为锚点，前后各取 1250 字。

④ 占位符改成行动指令：

```
"[已过期] 该工具结果因上下文预算被移出。如果结论依赖它，请重新调用对应工具
（FetchErrorLog / SearchInternalDoc / QueryGitCommit）取证，不要基于'看不到内容'直接下结论。"
```

**修复后**：`步数=4 耗时=9701ms tokens=10378+1213 工具=5(失败2)`，根因恢复。

### 学到什么（三层）

**排障方法论**：

> token 从 1.1 万掉到 4800，工具从 6 次掉到 4 次。**数值下降通常是坏信号，不是好信号**——
> 因为模型不是在变聪明，是在变瞎。

**设计取舍**：

> **淘汰策略不能按时间。** 排错场景里最早那条工具结果往往最重要（原始日志），后面都是围绕它做的验证。
> 淘汰顺序应该是：补充材料 → 中间的检索 → **最新的那条永远不扔**。
> 这跟 LRU 正好相反：LRU 假设「旧的用不到了」，Agent 假设「旧的恰恰是地基」。

**诚实承认**：

> 这个 bug 是我修上一个 bug 时引入的。**修 A 坏 B 在 Agent 工程里非常常见**，
> 因为每一步改动都在改变模型看到的输入，而模型行为是**涌现**的，不能静态推理。
> 之后的习惯是：每次改压缩/预算逻辑，都跑同一个 case 回归，对比 token 和步数，**数字突变就说明有问题**。

## 3. 错误信息也是 prompt

### 现象

`QueryGitCommit` 在一个还没有 `git init` 的目录里必然失败：

```
[step 2] ✗ QueryGitCommit 失败: 错误: git 返回码 128,
         stderr=fatal: not a git repository (or any of the parent directories): .git
```

模型连续重试 2 次，参数没变，结果自然没变。3 个固定 case 里**失败率 2/6 = 33%**。

### 对照组实验（这一段最有价值）

同一批任务里，`FetchErrorLog` 在文件不存在时返回的是：

```
错误: 日志文件不存在: logs/not_exist.log。可用文件: app.log
```

**模型一步就换成了 `app.log`，2 步收敛。**

同样是「失败」，一个让它原地打转，一个让它继续往前走。差别只在**错误信息里有没有下一步该做什么**。

### 学到什么

> **错误信息不是给程序员看的日志，是给模型看的 prompt。**
> 工具返回的每一个字符串，都会直接成为模型的下一轮输入。
> 所以工具报错时应该回答三件事：**错在哪、现在有什么可用、建议怎么改**。

## 4. 改了提示词，结果全面变差

### 背景：先量化「本来有多不稳」

同一个 case 连跑 4 次（工具失败全 0）：

| # | 步数 | prompt token | 工具数 | 答案字数 |
|---|---|---|---|---|
| 1 | 4 | 9426 | 6 | 2488 |
| 2 | 4 | 9875 | 6 | 2148 |
| 3 | 3 | 6876 | 4 | 2310 |
| 4 | 3 | 6887 | 4 | 2046 |

这是一组**双峰分布**：峰 A（6876/6887，群内差 0.2%）、峰 B（9426/9875，群内差 5%），**群间差 43%**。

对照：简单的纯知识问题连跑 4 次，prompt token 稳定在 4765~4771（**波动 < 0.2%**）。

> 同一个模型、同一份代码、同一句问法，简单 case 几乎确定，复杂 case 会分裂成两个「吸引子」——
> 差异只在于「要不要多查一轮 git 变更」，一次随机抖动就跨过了一个决策边界。

### 现象：改完更差

我往 `SYSTEM_PROMPT` 里加了 5 条规则，其中两条是：

3. 读懂错误原因再调整参数重试
5. 重试也要换参数或换工具

改后连跑 4 次：**7849 / 8604 / 14480 / 15150**。
prompt token 上限 **+53%**，波动从 43% 扩大到 **93%**。
更糟的是，本该 1~2 步的纯知识问题出现了 **1 步、0 工具调用、直接作答**——模型不查文档直接编。

### 根因

第 3 条给模型「换参数再试一次」的**正当理由**，第 5 条再次**鼓励换参数**。
两条叠加等于告诉模型：**重试是被允许的，只需要换个词。**
于是模型开始疯狂换关键词重复调同一个工具（参数不同，去重也拦不住）。

### 改法

`git checkout -- agent.py` 整体回滚。回滚后一次跑：**3 步 / 6901 token / 4 工具 / 2144 字**，落回原峰 A 区间。

### 学到什么

> **LLM 对多条指令是择优执行，不是全部执行。**

它不会 5 条都严格执行，它会挑**最容易满足的那几条**，并且**用新规则给自己的坏行为找理由**。

所以正确的分工是：**提示词用来给方向，代码用来保证底线。**
「同一调用不要重复」后来从提示词挪进了代码（`(工具名, 参数hash)` 去重，命中直接返回 `[跳过]`）——这才是模型绕不过去的硬约束。

> 补充一句更狠的：这次是回归脚本的**语义硬判断**（「答案里的证据引用消失了」）抓到的，
> 不是我肉眼看出来的。**没有基线就没有优化**。

## 5. 反直觉数字：预算压到 1/4，token 反而涨 45%

为了验证回归脚本不是摆设，我做了一次故障注入：把 `BUDGET_TOOL_RESULTS` 从 12000 临时**压到 3000（正常值的 1/4）**。

> 三个预算值别混：**6000 是初始值**（按「单条结果别太长」定的）、**6000→12000 是上文的修复动作**（翻倍）、
> **12000→3000 才是这里的实验**（压到 1/4）。

| | 正常 | 预算注入 3000 |
|---|---|---|
| 步数 | 4 | **7**（+75%） |
| prompt token | 10370 | **15083**（+45%） |
| 答案字数 | 1891 | **1047**（-45%） |

**机制**：日志压缩后 1852 字，占了 3000 预算的 62%。第 2 步工具结果一进来就爆表，
日志被挤出去 → 模型发现没有日志 → 重新 `FetchErrorLog` → 再挤一次。**恶性循环。**

> **越省上下文，模型花得越多、答得越差。** 预算不是越紧越好，紧了会让模型反复取证。

## 6. 评测集抓到的 bug：静默降级

两处分词缺陷，**都不会报错**——查询零分不抛异常、不打日志，结果列表照样返回 5 条，只是排序**退化成文档顺序**。

| 缺陷 | 现象 | 修复后 |
|---|---|---|
| 中文被切成 1 个 token（分词库缺失时的正则回退） | 整句查询在全库零命中 | 语义档 recall@5 0.125 → 0.750 |
| `snake_case` 与 `camelCase` 未归一化（`LEAK_DETECTION_THRESHOLD` vs `leakDetectionThreshold`） | 标识符查询零命中 | 语义档 recall@5 0.750 → **1.000** |

**8 条人工自检 8/8 全过**，两个 bug 一个都没抓到——因为自检用例的措辞和文档标题太接近。

> 自检证明「它能跑」，评测集才能证明「它跑得对」。

## 7. 幻觉的三种形态，一层比一层隐蔽

| 层 | 检查什么 | 结果 |
|---|---|---|
| 引用伪造 | 答案里的 `id` 是否是编的 | **0 条** —— 「幻觉率 0%」 |
| 该查不查 | 有没有调用过工具 | **9/25 条 0 次工具调用**，凭记忆作答 |
| 引用错配 | 引用是真的，但语义上推不出来 | **3/25 = 12%** |

**「幻觉率 0%」是个陷阱。** 指标只检查了「引用是不是编的」，而模型根本没打算编——
它直接不查。

`_check_grounding` 里原本写着：答案含「证据不足」就放行。而系统提示词又写着「宁可写当前证据不足」。
两条合起来形成了一条**合法逃逸路径**：不查 → 无证据 → 写「证据不足」 → 合规。

改法：**0 次工具调用直接判排查未完成**（代码级，不给提示词留解释空间），
提示词补上「涉及本系统组件必须先检索一次；确实要写证据不足，必须说明你查了什么、返回了什么」。

改后 9/25 → **0/25**，且 `log_missing` 那个 case 从「拿到文件不存在就收工」变成了「自动切换 app.log → 检索异常类型 → 给结论」。

> **给模型留的每一条免责声明，最后都会被用上。**

## 8. 单测抓到一个线上永远发现不了的 bug

压缩逻辑里有「最多保留 20 个栈帧」的上限。写边界单测（构造 100 帧）时发现**上限形同虚设**：

```python
# 改前
if EXC_LINE.search(ln):
    keep.append(ln); frame_count = 0    # 每条栈帧都命中 EXC_LINE，计数被清零
```

`EXC_LINE` 的正则包含 `at\s+[\w.$]+\(`，所以**每一条栈帧行都命中**，`frame_count` 每帧归零。

线上日志的栈通常只有 10 帧，所以从来不会暴露；但 Spring 代理链、深递归会有几十上百帧，会直接吃掉整个预算。

> **涉及上限/截断/丢弃的逻辑必须写边界单测**，因为正常路径永远走不到边界。

## 9. 其他踩过的坑（简记）

| 坑 | 教训 |
|---|---|
| reranker 没把握时**不报错、不返回空**，照样给完整排序，只是分数整体塌到 0.01~0.04 | 给 rerank 加了 top-1 阈值闸门，低于阈值退回融合排序 |
| 工具去重上线后触发率 **0%** | 约束层级选错了：拦的是字面重复，真正该拦的是语义重复。**诚实记录，不硬凑指标** |
| 回归脚本的基线被污染（把故障注入那轮的坏值存成了基线） | `--save-baseline` 只在确认结果合理时用 |
| 修改提示词后忘了跑回归就提交 | 任何改动提示词的提交都必须附回归结果 |
| 压缩逻辑改完只看了压缩率 | 压缩的输出必须做「关键行是否还在」的断言，不能只看比例 |

## 10. 如果重来一次，我会先做什么

1. **先建评测集，再写功能。** 没有评测的 Agent 项目等于没有方向盘——所有优化都只能靠感觉。
2. **每个改动配一个对照实验。** 上面有三次「改完更差」，全都是靠对照实验才发现的，靠肉眼一个都看不出来。
3. **区分「能跑」和「跑得对」。** 自检 8/8 和评测集 0.125 讲的是同一个系统。
4. **把提示词的活尽量交给代码。** 提示词给方向，代码保底线。
