# 常见故障排查手册

## 1. NullPointerException 排查

### 1.1 典型成因

Jackson 反序列化场景下的 NPE 有三类高频原因，按出现频率排序：

1. **字段缺失后未判空**：上游返回的 JSON 中缺少某个字段，`@JsonProperty` 未标 `required`，
   反序列化为 null 后直接参与运算。日志特征为 NPE 出现在 DTO 的 getter 调用之后。
2. **`@JsonSubTypes` 类型解析失败**：多态反序列化时 type 字段值不在已注册子类型中，
   Jackson 不会报错而是返回 null，调用方 NPE。特征是堆栈里出现 `TypeDeserializer`。
3. **静态初始化顺序**：`ObjectMapper` 被声明为 static 且在静态块中被提前使用。

### 1.2 定位步骤

- 从堆栈第一帧找到业务方法，确认 NPE 发生在 `getXxx()` 返回后还是集合遍历时。
- 若是集合遍历时 NPE，检查反序列化是否使用了 `FAIL_ON_NULL_FOR_PRIMITIVES`。
- 用 `curl` 重放原始请求体，对比线上与预发响应字段差异。

### 1.3 修复建议

在 DTO 上统一开启 `DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES`，
并在入口处增加字段校验（`@Valid` + `@NotNull`），把 NPE 提前暴露为 400 而非 500。

## 2. 数据库连接池耗尽

### 2.1 现象

日志出现 `HikariPool-1 - Connection is not available, request timed out after 30000ms`，
接口大面积超时，CPU 不高但线程数持续增长。

### 2.2 常见根因

- **长事务**：事务内调用了外部 HTTP 接口或 RPC，导致连接被占用数十秒。
- **连接泄漏**：手动 `getConnection()` 但异常分支未 close。
- **池大小配置不合理**：`maximumPoolSize` 小于并发需求，或远大于数据库 `max_connections`。

### 2.3 排查与修复

1. 打开 `leakDetectionThreshold`（建议 60000ms）拿到泄漏堆栈。
2. 检查 `activeConnections` 与 `idleConnections` 曲线，判断是突发流量还是持续占用。
3. 事务内禁止调用外部服务，改为事务外异步。
4. 池大小经验值：CPU 核数 × 2 + 磁盘数，且所有实例之和不超过 DB 最大连接数的 70%。

## 3. Redis 限流实现

### 3.1 滑动窗口 + Lua

两个方案的区别：固定窗口在窗口边界会出现双倍流量（前一秒末尾和后一秒开头都放行），
滑动窗口用 ZSET 记录每次请求时间戳，按时间范围 `ZCOUNT` 统计，边界平滑。

Lua 脚本在 Redis 中原子执行，避免 `ZCOUNT` 与 `ZADD` 之间的竞态：

```lua
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count >= limit then
  return 0
end
redis.call('ZADD', key, now, ARGV[4])
redis.call('PEXPIRE', key, window)
return 1
```

### 3.2 Token 额度限流

按请求次数限流无法控制成本，Agent 场景应按 token 计费：
从模型响应的 `usage` 字段累加 `prompt_tokens + completion_tokens` 到
`token:quota:{userId}:{date}`，用 `INCRBY` 累加并设置 24 小时过期，
超限时返回 429 并附剩余额度。注意流式响应需要在 `stream_options` 中显式开启 `include_usage`，
否则 usage 永远为空。

## 4. RabbitMQ 消息可靠消费

### 4.1 重复消费与幂等

MQ 承诺的是至少一次投递，重复消费是必然的。幂等做法：

- 消息体携带业务唯一键（如 `doc_id + content_hash`），消费前查唯一索引，存在则直接 ACK。
- 或在 Redis 用 `SETNX msg_id` 做去重窗口（TTL 24h）。
- 向量写入必须用 upsert 语义，不能用 add，否则重复消费会产生重复 chunk。

### 4.2 失败重试与死信

- `x-death` 计数重试 3 次后进入死信队列，DCQ 需人工确认或定时补偿任务捞回。
- 消费者要处理「状态卡在 PROCESSING」：加超时扫描任务，把超过 30 分钟未完成的任务重置为待处理。
- 大文档入库应分片：按页/章节拆成 N 个子任务并行消费，全部完成后聚合状态；
  任一失败标记 PARTIAL，避免一个坏页面阻塞整体。

## 5. SSE 流式响应中断

### 5.1 常见原因

- **Nginx buffering**：默认 `proxy_buffering on` 会把流式响应积攒成整块返回，
  前端表现为长时间无输出后突然吐出全部内容。需在响应头加 `X-Accel-Buffering: no`。
- **两级超时不匹配**：Java `SseEmitter` 的 timeout 必须大于 Python 侧整任务超时，
  否则后端还在推理、连接已被关闭，前端拿到半截内容。
- **空闲连接被杀**：长时间无数据时网关会断开，需要每 15 秒发送心跳事件（`event: ping`）。
- **客户端断开未取消下游**：用户关闭页面后模型仍在生成，浪费 token。
  需监听 IOException / 连接关闭事件，主动 cancel 上游调用。

## 6. JVM 内存溢出（OOM）排查

### 6.1 判断类型

- `java.lang.OutOfMemoryError: Java heap space` —— 堆内对象过多，需分析对象引用链。
- `unable to create new native thread` —— 线程数过多，查线程泄漏。
- `Metaspace` —— 动态生成类过多（CGLIB 代理、反射），检查类加载器泄漏。

### 6.2 步骤

1. 启动参数加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump`。
2. `MAT` 或 `jvisualvm` 打开 dump，看 dominator tree 找占比最大的对象。
3. 若是集合膨胀，检查是否有缓存未设上限（建议 Caffeine + maximumSize）。
4. 对比两次 dump 的 histo 结果，确认对象是否持续增长。

## 7. 向量索引与 Embedding 升级

### 7.1 换模型必须全量重建

不同 embedding 模型的向量空间不可比，混用会导致检索质量断崖式下降且难以察觉。
升级流程：

1. 新建索引 `kb_v2`，全量重新向量化（评估耗时，几百页文档通常需要 20 分钟以上）。
2. 用评测集在 v1 / v2 上各跑一遍 recall@k，确认 v2 不劣于 v1。
3. 通过别名切换（`kb_current -> kb_v2`），保留 v1 一周便于回滚。
4. chunk 上存 `content_hash`，用于增量更新与去重。

## 8. 混合检索与 RRF 融合

### 8.1 为什么不加权求和

BM25 分数的值域与余弦相似度完全不可比（前者受文档长度和词频影响，典型 0~30，
后者 -1~1），归一化后仍会随语料变化而漂移，权重需要反复调参且不稳定。

RRF（Reciprocal Rank Fusion）只用排名不用分数：

```
score(d) = Σ 1 / (k + rank_i(d))     k 通常取 60
```

好处是对两路分数分布完全不敏感，且天然抑制单路异常高分的支配。
代价是丢失了分数间距信息（第 1 名和第 2 名差距多大不影响融合结果）。

### 8.2 重排（Rerank）

召回 top 50 后交给 cross-encoder 精排（如 BGE-reranker）取 top 5。
收益是精度提升，代价是延迟增加，base 版本在 CPU 上对 50 条候选约需 100~300ms，
可用 batch 推理与候选数裁剪（50 → 30）来压延迟。
