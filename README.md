# DevPilot —— 线上故障排查 Agent

一个**多轮工具调用 Agent**：模型在「查内部文档 / 读错误日志 / 查 Git 提交」三类只读工具间自主决策取证，
输出「现象 — 根因 — 证据 — 修复建议」四段式结论，每条结论附可溯源的文档 chunk 引用。

> 这个项目的重点不是「跑起来一个 Agent」，而是**把 Agent 的效果量化出来，并找到它说谎的方式**。
> 下文所有数字都可在本仓库复现，见 [`numbers.md`](numbers.md)。

---

## 1. 它解决什么问题

线上报障时，人要做的事是：看日志 → 翻内部文档 → 查最近提交 → 判断根因。这是个**多步、有依赖、信息量超大的过程**：

- 一份 Java 异常日志有 **30571 字**（3000+ 行），塞不进上下文预算，而关键信息只在其中几行；
- 内部文档里同一个问题常被切成多块（配置在一个章节、用法在另一个章节）；
- 模型**不知道时可以编**，而排障场景下编错的代价很高。

所以这个 Agent 需要同时解决三件事：**会分解（循环）、能装下（压缩）、不乱说（取证与幻觉治理）**。

## 3. 三个设计决策（以及为什么不用现成方案）

### 3.1 手写 ReAct 循环，而不是套 LangChain

**原因**：排障场景下「工具失败」不是异常，**是要给模型看的信息**。

```
工具返回：错误: 日志文件不存在: logs/not_exist.log。可用文件: app.log
                        ↓ 模型据此自动换文件
工具返回：错误: 日志文件不存在: logs/not_exist.log。        ← 没有"可用文件"
                        ↓ 模型盲目重试 2 次后放弃
```

这是真实测出来的对照——**错误信息本身就是 prompt**。框架通常把工具失败抛成异常，
这个信息就丢了。

### 3.2 最大步数取 8，但它不是「最优值」

`MAX_STEPS` 不是拍脑袋，是跑了 **5 任务 × 4 档位 × 3 次 = 60 次**消融：

| MAX_STEPS | 收敛率 | 总 prompt tokens |
| --- | --- | --- |
| 3 | **6/15**（硬失败） | 82614 |
| 5 | 15/15 | 91783 |
| 8 | 15/15 | 90693（与 5 差 1.2%，**小于同档位抖动**） |
| 12 | 15/15 | **102017（+12.5%）** |

结论：**12 反而更贵**——上限放宽后模型会「再查一轮」，而第 N 步 prompt 含前 N-1 步全部内容，
每多一轮代价超线性。所以 8 不是测出来的最优值，是 **5 加一倍余量的安全值**。

> 注意：**步数 ≠ 工具调用数**。单轮可并发多个 tool_call，3 步就能调 6 个工具。
> 只限步数挡不住「一轮并发 20 个工具」，只限并发挡不住「无限轮询」，两个参数必须共存。

### 3.3 用 numpy 暴力余弦，而不是 chromadb

24 个 chunk 上 ANN 是杀鸡用牛刀：暴力余弦 `self._vectors @ q` 不到 1ms，
ANN 的收益拐点在十万级 chunk。引入向量库反而多一层「它到底为什么没召回」的黑盒。

代价是：**换 embedding 模型必须全量重建**（`load()` 校验 `vector_ids.json` 与 `chunks.json` 顺序一致，
不一致直接抛错，而不是静默用错向量）。

## 4. 评测：这个 Agent 到底行不行

这是项目的主体工作量。评测分两段：**检索准不准**、**说的是不是真的**。

### 4.1 检索评测（25 条三级评测集）

语料只有 24 个 chunk，所以**不能看着语料出题**——那样等于用答案找问题。
出题方式是「用户视角」：文档写「3.1 滑动窗口 + Lua」，题出成「为什么我的限流在整点附近会放过两倍请求」。

| 档位 | BM25 | bge-m3 向量 | 混合 + RRF | 混合 + RRF + rerank |
| --- | --- | --- | --- | --- |
| 全部 MRR | **0.931** | 0.836 | 0.917 | 0.910 |
| 语义档 recall@1 | 0.750 | 0.500 | 0.625 | **0.750** |
| 语义档 MRR | 0.854 | 0.653 | 0.812 | **0.854** |

rerank 的延迟：**p50 397ms / p95 573ms**（25 条全量），采信 22/25、闸门拦截 3/25。

**三个反直觉的发现**：

1. **向量检索在这个语料上输给 BM25**。原因是同模板故障手册的块间 cosine 均值就有 **0.5679**
   （std 0.069），而 S1 的 gold 块只有 **0.5667（z≈−0.01）**——等于随机块平均值，首命中排到第 7。
   「整点附近放过两倍」↔「固定窗口边界」是**推理关系**，不是语义相似，embedding 不负责这件事。
2. **rerank 直接接上去反而变差**（1 条变好、19 条不变、**4 条变差**）。因为 reranker 没把握时
   **不报错、不返回空，照样给完整排序**，只是分数塌到 0.007~0.038。于是加了 top-1 阈值闸门（0.10）。
3. **`recall@5 = 1.000` 不能当好消息**：5 个块占 24 个 chunk 的 21%，这是理论上限附近。
   所以看的是档位之间的差，不是绝对值。

### 4.2 幻觉评测：三层递进

第一版指标只查「引用伪造」（答案里的 id 是否真实存在于语料），**结果幻觉率 0.0%** —— 这个数字是假的。

| 层级 | 查什么 | 结果 |
| --- | --- | --- |
| 第一层：引用伪造 | 引用的 chunk_id 是否真实存在 | 0/25 |
| 第二层：**该查不查** | 是否根本没调用工具就作答 | **9/25 → 0/25**（修复后） |
| 第三层：引用错配 | 引用真实，但语义上推不出结论 | **12%（3/25）** |

**第二层是最值钱的发现**。9 条题里，有 8 条的正确答案就躺在检索 top1 里，但模型 0 工具调用、
凭记忆作答，然后写一句「当前证据不足，建议补充信息」——**给自己开了免责声明**。

链条是：`不查 → 无证据 → 写"证据不足" → 代码判定"诚实" → 放行`，一条**合法的逃逸路径**。

修法是两层叠加：
- 提示词层：只要问题涉及本系统组件，**必须先调一次检索**再决定用不用；
- **代码层：`tool_calls_total == 0` 直接标记降级** —— 不看提示词相信它。

第三层用 LLM-as-judge 补上，并诚实记录：**judge 自己也会出错**（它把一条接近「不支撑」的判成了「部分支撑」）。
所以规则层和 judge 层是**互补而非替代**。

## 5. 上下文工程：30571 字 → 1852 字

日志压缩不是截断，是**抽取式压缩**：

1. 保留所有异常行（`Exception` / `Caused by` / `Error`）；
2. **保留异常行后的续行描述**（真正的 `Cannot deserialize value of type ...` 在下一行）；
3. 栈帧上限 20 帧，其余丢弃；
4. 全丢 INFO/DEBUG 噪声行；
5. 压缩率不达标时退化为 head_tail，并在输出里标 `[中间省略 N 行]`。

原文不丢：存到 `traces/<id>/tool_results/<handle>.txt`，模型需要时用 `FetchToolResult` 按需取回
（取回时只返回锚点附近的 2500 字窗口，避免再把上下文撑爆）。

压缩率 **93.9%**。但更重要的是：**压缩后模型仍能准确说出 `data.tags` 是 JSON 对象、
DTO 声明为 `List<String>`、错误位置在 `line: 1, column: 62`** —— 这才是压缩的目标。

> 有一次修复让压缩率从 18.7:1 变成 16.5:1（变"差"了 217 字），但那 217 字是把被误删的异常描述捡回来。
> **压缩的目标是保住推理所需的证据，不是数字好看。**

## 6. 快速开始

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt --only-binary=:all:

copy .env.example .env      # 填 DEEPSEEK_API_KEY 与 EMBEDDING_API_KEY

python make_log.py 3000 --mix     # 生成 30571 字的模拟日志
python build_index.py             # 建索引 + 8 条自检（8/8 top1 命中）
python main.py "线上报 UserService 空指针，日志在 logs/app.log，帮忙定位"
```

**复现评测**：

```powershell
python eval_rag.py --dump         # 四组检索对比 → .index/eval_rag_result.json
python eval_hallucination.py      # 25 条完整 Agent 运行 → hallucination.json
python eval_grounding_judge.py    # LLM-as-judge 引用错配 → grounding_judge.json
python ablate_steps.py --repeat 3 # 4 档位 × 5 任务 × 3 次消融
python test_compact.py            # 压缩逻辑 8 例边界单测
python regress.py                 # 3 个固定 case 的回归快照
```

> 检索评测是**确定性**的（同样输入同样结果）；幻觉与 judge 走 LLM，**每次跑会变**，
> 仓库里保存的是单次快照，不是多次平均。

## 7. 已知局限（主动交代）

| 局限 | 为什么没做 |
| --- | --- |
| 语料只有 24 个 chunk，`recall@5` 接近理论上限 | 造语料不是这个项目的重点，评测方法论才是；已用「看档位差、不看绝对值」规避 |
| 25 条评测集由我按用户口吻编写，存在设计者偏差 | 已在 `eval_set.py` 中标注为 dev set，缓解手段是「不照抄文档标题、用真实提问口吻」 |
| 幻觉率与引用错配是单次快照，未做多次平均 | 一轮 25 条完整 Agent 运行需十几分钟，时间成本高于收益 |
| `QueryGitCommit` 查的是本仓库 | demo 里没有真实业务仓库，属演示性质 |
| ACL 用文件名后缀模拟 | 生产应从文档元数据/权限系统同步，检索层做 metadata filter |
| 未实现 SSE 流式端点与 Redis 会话记忆 | 取舍：把时间花在评测上而不是再加一层功能 |
| 单轮任务专用，循环未抽象成通用 harness | 下一步计划：抽出 `TaskSpec`，用第二个任务验证通用性 |

## 9. 这个项目踩过的坑

开发过程中遇到的全部问题（含 3 次把功能改坏又改回来的完整记录）整理在
[`docs/development-log.md`](docs/development-log.md)，其中比较有代表性的：

- 分词把整句中文切成 1 个 token，**所有查询零分、排序静默退化为文档序**——不报错、不打日志；
- 预算调小反而让 token 多花 45%、答案少 45%（模型重新取证，恶性循环）；
- 一次 prompt 优化把波动从 43% 放大到 93%，**根因是两条指令互相抵消**，最终回滚；
- 单测抓到一个线上永远发现不了的 bug：栈帧计数被每条栈帧重置，导致「最多 20 帧」形同虚设。
